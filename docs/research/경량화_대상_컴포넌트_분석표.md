## 4. 병목 지점 분석

### 4.1 orchestration.yaml 직렬 대기 구간

모든 `team_profiles` (global_orchestrator, research_strategy, engineering_delivery, design_strategy, product_strategy, growth_strategy, ops_delivery 등 7개 프로파일) 에서 `execution_mode: sequential`이 설정되어 있다.

이는 설계 의도(DEPENDS 기반 직렬 태스크 흐름)이지만, 실질적으로 **모든 부서 간 태스크가 순차 처리**됨을 의미한다. 병렬 실행 가능한 독립 서브태스크도 직렬로 대기하게 된다.

`pm_orchestrator.py` 내부 주석에도 "Only use 'none' when tasks are truly parallelizable"이라고 명시되어 있어, 병렬화 기회가 있어도 보수적으로 직렬 처리 중임을 확인.

### 4.2 타임아웃 설정 현황

| 설정 위치 | 값 | 내용 |
|-----------|-----|------|
| `docker-compose.yml` - gemini 봇 환경변수 | `GEMINI_CLI_DEFAULT_TIMEOUT_SEC=1800` | **30분** — gemini_cli_runner.py 기본 타임아웃. 성장실·리서치실 봇 2개에 적용 |
| `tools/gemini_cli_runner.py` | `DEFAULT_TIMEOUT = int(os.getenv("GEMINI_CLI_DEFAULT_TIMEOUT_SEC", "1800"))` | 환경변수 없을 때도 1800초 기본값 |
| `main.py` CONFLICT_WAIT | `70초` | Telegram 폴링 충돌 시 재연결 대기 |
| `main.py` RESTART_WAIT | `5초` | 정상 종료 후 자동 재시작 대기 |
| `orchestration.yaml` - autonomous_loop | `idle_sleep_sec: 300` | 자율 루프 5분 대기 사이클 |
| `orchestration.yaml` - goal_tracker | `poll_interval_sec: 30` | 서브태스크 완료 폴링 주기 |
| `docker-compose.yml` - bot healthcheck | `interval: 60s, start_period: 30s` | 헬스체크 주기 |

**주요 위험**: Gemini CLI 1800초 타임아웃은 단일 태스크가 30분간 응답 없이 블로킹될 수 있음을 의미. 직렬 실행 모드와 결합되면 전체 파이프라인이 최대 30분 × N 태스크로 지연될 수 있다.

### 4.3 기타 병목 패턴

**1. telegram_relay.py 과대 집중**: 4,789 LOC 단일 파일이 메시지 수신, 라우팅, 릴레이, 명령어 처리, 아티팩트 인덱싱, 레거시 봇 설정 갱신 등 다수 책임을 담당. 코드 변경 시 충돌 위험 높음.

**2. Redis 선언 vs 실제 사용 불일치**: docker-compose.yml에서 Redis(6379)를 모든 봇 공통 인프라로 선언하고 `REDIS_URL` 환경변수를 주입하지만, core/ 및 tools/ 내 코드에서 `import redis` 또는 `from redis` 패턴이 전혀 발견되지 않음. Redis가 선언만 되고 실제 코드에서 미사용 상태일 가능성 있음 — 불필요한 컨테이너 오버헤드.

**3. 다중 DB 파일 동시 운영**: 루트에 `ai_org.db`, `context.db`, `pm_tasks.db`, `tasks.db` 4개 SQLite 파일이 존재. 분산 쓰기 패턴으로 aiosqlite lock 경합 가능성.

**4. 스케줄러 중복 실행 위험**: `core/scheduler.py` (1,209 LOC)와 `orchestration.yaml`의 `daily_goal_pipeline` 크론 설정이 공존. cron `"0 0 * * *"` 및 `"30 14 * * *"` 훅이 스케줄러 코드 내 APScheduler 크론과 별도 경로로 실행될 경우 중복 트리거 위험.

## 6. 핵심 권고사항 3선

1. **Hermes 미사용 모듈 군 즉시 제거**: `core/hermes_integration.py`, `core/tool_registry.py`, `core/platform_adapter.py` 3개 파일은 런타임에서 단 한 곳도 import하지 않는 데드코드다. 기존 PRD(`docs/prd/hermes-integration-spec.md`)에서도 이를 인지하고 있음. 삭제 시 core/ 모듈 수 감소 및 향후 리팩토링 혼선 방지 효과가 즉각적이다.

2. **Redis 컨테이너 제거 또는 실제 연결 구현 결정**: docker-compose.yml의 `aiorg-redis` 서비스는 모든 봇이 `depends_on`으로 의존하는 필수 컨테이너인데, 애플리케이션 코드 어디서도 Redis를 import하거나 연결하지 않는다. 현재는 기동 지연(healthcheck 10초 × 5회)만 유발하는 빈 인프라다. "Redis 도입 vs 제거"를 명시적으로 결정하고, 도입하지 않을 경우 docker-compose.yml에서 삭제해 컨테이너 기동 시간을 단축해야 한다.

3. **Gemini CLI 타임아웃 1800초 단축 + 직렬 실행 모드 부분 병렬화**: 현재 전 부서 `execution_mode: sequential` + Gemini 기본 타임아웃 30분 조합은 최악의 경우 N개 태스크 × 30분 지연을 유발한다. 타임아웃을 600초로 단축하고, `pm_orchestrator.py`의 DEPENDS 그래프에서 의존 관계 없는 태스크에 병렬 실행을 허용하면 전체 파이프라인 응답 시간을 구조적으로 개선할 수 있다.
