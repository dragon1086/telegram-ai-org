## 1. 배경 및 목적

피드백이 유입될 때 "어떤 인프라 환경 버전에서 발생한 이슈인가"를 즉시 식별할 수 없으면,
스펙 문제(기획/설계 결함)와 인프라 노이즈(환경 변화로 인한 이상치)가 뒤섞여 디버깅 비용이 증가한다.

**목적**: 모든 피드백 채널·로그·문서에 `infra_baseline_version` 태그를 함께 기재하는
**컨벤션 표준**을 수립하여, 수신 즉시 이슈 분류 가능한 구조를 만든다.

---

## 2. 적용 범위

| 채널 | 적용 대상 | 태깅 시점 |
|------|-----------|-----------|
| **텔레그램 피드백** | 봇 응답·대화 스레드 내 이슈 보고 | 이슈 보고 메시지 수신 즉시 |
| **E2E 테스트 로그** | `logs/e2e_preflight_latest.log` | pre-flight 체크 헤더 자동 삽입 (RETRO-10 위임) |
| **회고 문서** | `docs/retros/YYYY-MM-DD.md` | 회고 작성 시 문서 상단 메타 블록 |
| **이슈 트래커** | L1 Active 태스크, 태스크 ID | 태스크 생성 시 |
| **리서치 산출물** | `research_context.yaml` | 조사 시작 전 (RETRO-08 연계) |
| **실험 로그** | `logs/experiment_log.yaml` | 실험 항목 추가 시 (RETRO-07/13 연계) |

> **범위 외**: 텔레그램 일반 대화(비이슈), 개인 메모, 임시 스크래치 파일은 태깅 의무 없음.

## 3. 태깅 포맷 표준

### 3-A. 인라인 태그 (텍스트 본문 삽입)

```
[infra:v1.2.0] 이슈 내용 또는 피드백 본문
```

- 접두어: `[infra:<semver>]`
- 버전 형식: `v{MAJOR}.{MINOR}.{PATCH}` — `infra-baseline.yaml`의 `baseline_version` 필드값과 동일
- 위치: 피드백/이슈 첫 줄 또는 제목에 포함

**예시**:
```
[infra:v1.2.0] E2E 전체 타임아웃 — timeout 파라미터 재확인 필요
[infra:v1.2.0] 봇 응답 지연 300ms → 스펙 문제인지 인프라 문제인지 분류 필요
```

### 3-B. 구조화 태그 (YAML/JSON 메타 블록)

문서·로그·구조화 파일에서는 메타 필드로 기재한다.

```yaml
# 회고 문서 상단 메타
retro_meta:
  date: "2026-03-29"
  infra_baseline_version: "v1.2.0"
  sprint: "RETRO-2026-03"
```

```yaml
# 태스크 메타 (L1 Active 확장 시)
infra_baseline_version: "v1.2.0"
```

### 3-C. 버전 확인 방법

```bash
# infra-baseline.yaml에서 현행 버전 확인
grep "baseline_version:" config/infra-baseline.yaml
# 또는
cat logs/e2e_preflight_latest.log | grep "baseline_version"
```

## 4. 이슈 분류 기준: 스펙 이슈 vs 인프라 노이즈

이슈 수신 후 아래 기준으로 1차 분류한다.

| 분류 | 정의 | 판단 기준 | 담당 |
|------|------|-----------|------|
| **스펙 이슈** | 설계/요구사항 결함 | 인프라 버전 동일 + 동일 조건에서 재현됨 | 기획실 → 개발실 |
| **인프라 노이즈** | 환경 변수 변경으로 인한 이상치 | infra_baseline_version 변경 시점과 이슈 발생 시점 일치 | 운영실 |
| **복합 이슈** | 스펙 + 인프라 동시 변화 | 두 버전이 동시에 바뀐 구간 | 기획실 + 운영실 공동 |
| **미분류** | 태그 없거나 버전 불명 | `[infra:unknown]` 표시 | 기획실이 버전 추적 후 재분류 |

### 분류 플로우

```
피드백 수신
    │
    ▼
[infra:vX.Y.Z] 태그 있는가?
    │ YES                  NO
    ▼                      ▼
현행 baseline과        [infra:unknown] 처리
버전 동일?             → 운영실에 버전 확인 요청
    │ YES      NO
    ▼          ▼
스펙 이슈   인프라 노이즈
검토        or 복합 이슈
```

## 5. RETRO-10과의 역할 분담

| 항목 | RETRO-06 (기획실) | RETRO-10 (운영실) |
|------|-------------------|-------------------|
| **담당 채널** | 텍스트 피드백, 문서, 이슈 트래커 | E2E 로그 헤더 자동 삽입 |
| **태깅 방식** | 수동 컨벤션 (인라인/YAML 메타) | 자동화 (`_print_preflight_header()`) |
| **버전 소스** | `infra-baseline.yaml` 수동 참조 | conftest.py가 런타임에 자동 읽기 |
| **중복 여부** | ❌ 중복 없음 — 채널·자동화 여부로 완전 분리 |

> E2E 로그의 `baseline_version` 자동 삽입은 **RETRO-10 완료로 커버됨**.
> RETRO-06은 E2E 이외 모든 채널의 **수동 태깅 컨벤션**을 담당한다.

## 6. 예외 처리 규칙

| 상황 | 처리 방법 |
|------|-----------|
| 버전 불명 피드백 | `[infra:unknown]` 태그 후 기획실이 운영실에 버전 조회 |
| 긴급 이슈 (즉시 대응 필요) | 태깅 없이 우선 대응, 사후 48시간 내 태그 보완 |
| infra-baseline.yaml 미갱신 구간 | 이전 버전 유지, 변경 시 기획실 공지 |
| 여러 버전 혼재 (롤백/카나리) | 범위 형식 사용: `[infra:v1.1.0~v1.2.0]` |
