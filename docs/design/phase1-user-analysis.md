## 2. 사용 시나리오 분석

### 시나리오 1 — 초기 셋팅

**대상 페르소나**: A (기술자), B (비기술자, 개발자에게 위임)

#### 현재 흐름 (As-Is)

```
1. GitHub README 진입
2. 의존성 수동 확인 (Python 버전, 텔레그램 봇 토큰 생성법 별도 검색)
3. git clone + cd
4. pip install -r requirements.txt (venv 설정 수동)
5. .env 파일 수동 생성 (.env.example 참고)
6. 봇 토큰, 엔진 API 키 입력
7. python main.py 실행
8. 오류 발생 시 로그 수동 확인 → 원인 파악 → 수정 반복
```

**Pain Points:**
- 단계가 8개 이상으로 인지 부하가 높음
- .env 필수 키 vs 선택 키 구분 없음 → 과다 입력 피로
- 첫 오류 시 디버깅 경로 불명확 (에러 메시지가 스택트레이스 그대로)
- 비기술자는 3단계에서 이미 이탈

#### 개선 후 흐름 (To-Be)

```
1. README Quick Start 블록에서 3줄 복사
   git clone ... && cd telegram-ai-org && bash scripts/setup.sh
2. setup.sh가 Python 버전·venv·의존성 자동 처리
3. 대화형 프롬프트로 필수 토큰만 입력 (5개 이하)
4. .env 자동 생성 + pre-flight 체크 자동 실행
5. pre-flight 통과 시 "Ready to launch" 출력 + 실행 명령 안내
6. pre-flight 실패 시 항목별 원인 + 해결 방법 한국어로 출력
```

**기대 개선값:**
- 설치 시간: 30분 → 10분 이내
- 첫 오류 해결 경로: 로그 수동 탐색 → pre-flight 리포트 즉시 확인
- 비기술자 성공률: 추정 20% → 60% 이상 (Docker 원라이너 제공 시)

### 시나리오 2 — 일상 운영

**대상 페르소나**: B (기획자/운영자), C (파워유저)

#### 현재 흐름 (As-Is)

```
1. 텔레그램에서 PM봇에게 업무 지시 메시지 전송
2. PM봇이 내부적으로 태스크 분류 → 부서봇 디스패치
3. 부서봇 응답 대기 (응답 시간 불투명)
4. 응답 도착 — 단순 텍스트 블록
5. 후속 지시 또는 수정 요청
6. 봇 무반응 시 원인 불명 → 서버 재기동 또는 포기
```

**Pain Points:**
- 태스크가 어느 봇에 배분됐는지 사용자에게 안 보임
- 처리 중 진행 상태(progress) 피드백 없음 → "고장났나?" 불안
- 오류 메시지가 기술 용어(exit 143, SIGTERM 등) 그대로 노출
- 명령어를 외워야 사용 가능 (디스커버빌리티 낮음)
- `/help` 응답이 텍스트 덤프 형태로 가독성 낮음

#### 개선 후 흐름 (To-Be)

```
1. 텔레그램에서 PM봇에게 메시지 전송
2. PM봇이 "개발실로 전달중..." 즉각 확인 메시지 (1초 이내)
3. 처리 중 진행바 또는 단계 표시 ("분석 중 → 코드 작성 중 → 검토 중")
4. 완료 시 구조화된 응답 + 인라인 키보드로 후속 액션 제안
5. 오류 시 사람 말로 원인 설명 + "다시 시도" / "운영자 호출" 버튼 제공
6. /help → 카테고리별 인라인 키보드 메뉴 (입력 필요 없음)
```

**기대 개선값:**
- 사용자 불안감: 즉각 확인 메시지로 "처리 중" 인지 → 이탈률 감소
- 오류 이해도: 기술 용어 제거 → 비기술자 자가 해결 비율 증가
- 명령어 디스커버빌리티: 인라인 키보드로 50% 이상 입력 부담 감소

### 시나리오 3 — 실시간 모니터링

**대상 페르소나**: A (개발자), C (파워유저)

#### 현재 흐름 (As-Is)

```
1. 서버 SSH 접속
2. tmux / screen으로 로그 스트림 확인
3. 봇 상태를 로그 텍스트에서 수동 파악
4. GoalTracker 상태를 코드/DB 직접 조회
5. watchdog 타임아웃 발생 시 exit 143 로그 확인 후 수동 재기동
6. 이상 상황 파악까지 평균 5~15분 소요
```

**Pain Points:**
- 모니터링이 터미널에 묶여 있어 모바일 접근 불가
- GoalTracker 상태머신 현재 상태가 외부에 노출되지 않음
- 만화 캐릭터 컨셉 대시보드가 코드에 정의되어 있으나 실제 렌더링 미구현
- pre-flight 결과가 E2E 로그 헤더에만 있고 실시간 노출 채널 없음
- 봇별 활성 태스크 수, 응답 latency 집계 수단 없음

#### 개선 후 흐름 (To-Be)

```
1. 텔레그램 모니터링 채널에서 대시보드 메시지 실시간 갱신
2. 각 부서봇이 만화 캐릭터 아이콘 + 현재 상태 (Idle / Working / Blocked)로 시각화
3. GoalTracker 진행률을 % 또는 단계 텍스트로 표시
4. watchdog 이벤트 발생 시 즉시 알림 + 원인 요약
5. /status 명령어로 전체 조직 상태 스냅샷 텍스트 대시보드 조회
6. ALERT-04 알림 규칙과 연동해 임계값 초과 시 자동 알림
```

**기대 개선값:**
- 이상 상황 감지 시간: 5~15분 → 30초 이내
- 모바일 모니터링 가능 → 운영 유연성 향상
- 만화 캐릭터 시각화로 봇 상태의 직관성 극대화

### 시나리오 4 — 원격 접근 / 지원

**대상 페르소나**: B (운영자), C (파워유저)

#### 현재 흐름 (As-Is)

```
1. 서비스 이상 감지 (사용자 제보 또는 우연 발견)
2. SSH 터널링으로 서버 접속
3. 로그 파일 수동 탐색 (grep / tail)
4. 원인 파악 후 수동 수정 또는 재기동
5. 수정 결과를 슬랙/텔레그램으로 수동 공유
6. 재발 방지 조치 미흡
```

**Pain Points:**
- 원격 진단 → 조치 → 보고의 흐름이 완전히 수동
- 비기술 운영자는 SSH 접근 자체가 불가
- dashboard-tunnel 구성이 있으나 설정 문서가 분산되어 있음 (`docs/dashboard-tunnel-comparison.md`)
- 원격 지원 요청 채널이 없음 (텔레그램 봇을 통한 SOS 흐름 미정의)

#### 개선 후 흐름 (To-Be)

```
1. 사용자가 텔레그램에서 /sos 또는 "도움 요청" 메시지 전송
2. PM봇이 현재 시스템 상태 자동 진단 리포트 생성
3. 진단 결과를 운영자 채널에 자동 포워딩
4. 운영자가 텔레그램 인라인 키보드로 "재기동" / "설정 확인" / "에스컬레이션" 선택
5. 조치 완료 후 자동 결과 보고 메시지
6. 재발 방지: RETRO 아이템으로 자동 등록
```

**기대 개선값:**
- 원격 진단 접근성: SSH 불필요 → 텔레그램만으로 1차 대응 가능
- 비기술 운영자 자가 해결 범위 확장
- 사후 회고 자동화로 재발률 감소

## 3. 사용성 문제 우선순위 매트릭스

> 심각도(Severity)와 발생 빈도(Frequency)를 기준으로 2x2 매트릭스를 구성합니다.
> **심각도**: 사용자 목표 달성에 미치는 영향 (High = 목표 달성 불가 / Low = 불편함 수준)
> **빈도**: 얼마나 자주 발생하는가 (High = 매 세션 / Low = 드물게)

### 매트릭스 구성

```
                     빈도 낮음 (Low Frequency)
                              │
          Q3 [낮은 우선순위]   │   Q1 [즉시 수정 필요]
          ─────────────────────┼─────────────────────
          Q4 [모니터링]        │   Q2 [개선 권장]
                              │
                     빈도 높음 (High Frequency)

     ◄──────── 심각도 낮음 ────────┼──────── 심각도 높음 ────────►
```

### Q1 — 즉시 수정 필요 (High Severity × High Frequency)

## 4. WCAG 2.1 AA 접근성 요구사항

> **적용 환경**: 텔레그램 메시지 인터페이스 (모바일 앱 + 데스크탑 앱 + 웹 클라이언트)
> **기준 레벨**: WCAG 2.1 AA (핵심 흐름은 AAA 권장)
> **연관 문서**: `docs/RETRO-23-ui-execution-blocking-pattern.md §6`, `config/design-baseline.yaml`

### 4-1. 텔레그램 메시지 환경 제약 이해

텔레그램은 표준 웹 DOM이 아닌 네이티브 앱 환경이므로 WCAG를 직접 적용할 수 없습니다. 아래 항목들은 **봇이 생성하는 메시지 콘텐츠** 레이어에 적용 가능한 접근성 원칙을 실용적으로 해석한 것입니다.

| WCAG 원칙 | 텔레그램 적용 가능 범위 |
|-----------|----------------------|
| **인식 가능 (Perceivable)** | 텍스트 대안, 구조적 마크업, 색상 의존성 배제 |
| **운용 가능 (Operable)** | 키보드 접근성 (데스크탑 클라이언트), 충분한 터치 타깃 |
| **이해 가능 (Understandable)** | 명확한 언어, 오류 식별 및 설명 |
| **견고성 (Robust)** | 다양한 텔레그램 클라이언트 호환성 |

---

### 4-2. 색상 대비 요구사항 (WCAG 1.4.3 / 1.4.11)

텔레그램 봇 메시지에서 색상을 직접 제어할 수 없으나, 인라인 키보드 버튼 레이블과 이모지 사용에 아래 원칙을 적용합니다.

| 항목 | 요구사항 | 적용 방법 |
|------|---------|----------|
| **일반 텍스트** | 대비율 4.5:1 이상 | 텔레그램 기본 테마 의존. 커스텀 HTML 마크업 사용 시 적용 |
| **대형 텍스트 (18pt+ / 14pt+ Bold)** | 대비율 3:1 이상 | 섹션 헤더에 `**굵게**` 사용 시 적용 |
| **상태 표시** | 색상만으로 상태를 전달하지 않음 | 이모지 + 텍스트 레이블 병행 (예: "BLOCKED" 텍스트 필수) |
| **경고/오류 색상** | 색상 + 아이콘 + 텍스트 3중 표현 | RETRO-23 severity 3단계 패턴 준수 |

**severity 3단계 접근성 매핑** (RETRO-32 기준):

| 단계 | 색상 의미 | 이모지 | 텍스트 레이블 | 대비 기준 |
|------|----------|--------|--------------|----------|
| **INFO** | 파랑 계열 | `ℹ️` | `[INFO]` | 4.5:1 이상 |
| **WARNING** | 주황 계열 | `⚠️` | `[경고]` | 4.5:1 이상 |
| **CRITICAL** | 빨강 계열 | `🚨` | `[차단됨]` | 4.5:1 이상 |

## 핵심 인사이트 요약

1. **비기술자(페르소나 B)의 이탈은 초기 8단계 셋팅과 봇 무반응 시 피드백 부재에서 발생한다.** 즉각적인 "처리 중" 상태 메시지와 3줄 Quick Start가 이탈을 막는 가장 빠른 처방이다.

2. **Q1 우선순위 4개 문제(U-01~U-04)는 모두 피드백 공백 문제다.** 봇이 뭔가 하고 있다는 신호를 주지 않아 사용자가 고장으로 판단한다. 실시간 상태 메시지 1초 이내 응답이 핵심이다.

3. **만화 캐릭터 실시간 대시보드는 페르소나 B의 "모니터링 불투명" 페인을 해소하는 동시에, 페르소나 A/C에게는 시스템 상태의 직관적 진단 도구가 된다.** 단순한 시각화가 아니라 상태 신호 채널로 설계되어야 한다.

4. **접근성 P1 항목 3개는 모두 구현 난이도가 낮다.** 오류 메시지 텍스트 수정, 이모지+텍스트 병행, 인라인 키보드 레이블 길이 확보는 코드 변경 없이 프롬프트 또는 메시지 템플릿 수정만으로 적용 가능하다.

5. **파워유저(페르소나 C)의 핵심 요구는 "설계 의도의 문서화"다.** 코드는 읽을 수 있으나 ADR(Architecture Decision Record)과 상태머신 전이 다이어그램이 없으면 신뢰 기반 기여가 어렵다. RETRO-27 기준 추적 YAML과 연동한 문서화가 C 세그먼트 유지의 열쇠다.
