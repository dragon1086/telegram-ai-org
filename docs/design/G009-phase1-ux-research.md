## 1. 배경 및 문제 정의

### G009 현황 요약

| 필드 | 내용 |
|------|------|
| **목표 ID** | G-aiorg_pm_bot-009 |
| **목표명** | AIMesh 경량화 · 대시보드 · 오픈소스화 통합 PRD |
| **종료 상태** | `max_iterations_reached` (이터레이션 11/10 초과) |
| **달성률** | 0/2 KR (confidence 0.0 — 미달성) |
| **산출물** | 리서치실 3개 완료, 기획실/디자인실 등 다수 미수신 |
| **종료 시각** | 2026-04-01 05:35:46 KST |

### 문제 정의

PM(Rocky)이 GoalTracker에 부여한 장기목표가 `max_iterations_reached` 상태로 종료된 이후, **결과를 어떻게 파악하고 후속 액션을 결정하는가**에 대한 UX 흐름이 설계되어 있지 않다. 현재는 로그 파일과 JSON 상태 파일을 직접 뒤져야 하며, 30초 내 핵심 정보 파악이 불가능하다.

## 2. 페르소나 정의

### 페르소나 1 — PM Rocky (주요 사용자)

| 항목 | 내용 |
|------|------|
| **이름** | Rocky (PM) |
| **직책** | 프로덕트 매니저 / 봇 조직 총괄 |
| **기술 수준** | CLI 경험 있음, Python 기본 이해, 텔레그램 봇 운영 주체 |
| **사용 기기** | 맥북 (개발 환경) + 스마트폰 텔레그램 (모니터링) |

#### 목표 (What they want)

- 텔레그램에서 "G009 결과 어떻게 됐어?" 한 문장으로 결과 조회
- 30초 이내에 핵심 상태(달성/미달성/이터레이션 초과)를 파악
- 산출물이 어디에 저장됐는지 즉시 알고 싶음
- 미달성 원인이 이터레이션 한도 초과인지, 태스크 실패인지 구별하고 싶음
- 후속 액션 (목표 재설정 / 산출물 활용 / 목표 폐기) 결정을 즉각적으로 내리고 싶음

#### Pain Points (현재 문제)

1. **정보 분산**: G009 결과가 `logs/goal_tracker_dispatch.log`, `reports/ops/goal_tracker_stage_state.json`, `.omx/reports/G-aiorg_pm_bot-009-telegram-report.md` 등 3곳에 분산. 어느 파일이 최신인지 불분명.
2. **상태 불투명**: `max_iterations_reached`가 "실패"인지 "부분 완료"인지 즉시 해석 불가능. 달성률 0/2와 산출물 3개 생성이 공존하는 모순적 상황.
3. **pm_progress_guide.md 미동기화**: GoalTracker DB에는 G009가 존재하지만 pm_progress_guide.md에 등록되지 않아 메모리 레이어 간 불일치 발생.
4. **후속 액션 안내 없음**: 종료 상태 확인 후 "그래서 뭘 해야 하나"에 대한 안내가 없어 재설정 여부를 스스로 판단해야 함.
5. **텔레그램 응답 포맷 부재**: 텔레그램에서 목표 상태를 요청해도 구조화된 요약 메시지가 아닌 원시 로그나 긴 텍스트로 응답됨.

#### 사용 시나리오 (G009 결과 조회)

```
[상황] 오전에 G009를 배정했고, 저녁에 결과를 확인하려 함
[채널] 텔레그램 PM 채널
[질문] "G009 결과 어떻게 됐어?"
[기대] 10초 이내 상태 배지 + 달성률 + 핵심 산출물 목록 확인
[다음] 결과 기반으로 후속 G010 목표 설정 or 산출물 검토 지시
```

### 페르소나 2 — 팀 리더 (부차 사용자)

| 항목 | 내용 |
|------|------|
| **이름** | 팀 리더 (부서장) |
| **직책** | 개발실/기획실/디자인실 등 부서 책임자 역할 수행하는 봇 오케스트레이터 |
| **기술 수준** | 산출물 품질 판단 가능, 후속 배정 결정 주체 |
| **사용 기기** | 부서 텔레그램 채널 (봇 대화 공간) |

#### 목표 (What they want)

- 자신의 부서가 G009에서 어떤 태스크를 수행했고 어떤 산출물을 냈는지 확인
- 미수신 태스크(결과 없음으로 기록된 항목)의 원인 파악
- G009 후속으로 어떤 태스크가 재배정될지 예측하여 준비
- 산출물의 품질이 승인 가능한지 검토 후 PM에게 피드백 전달

#### Pain Points (현재 문제)

1. **부서별 참여 현황 불가시**: 어느 부서가 결과를 제출했고 어느 부서가 미수신 상태인지 한눈에 보이지 않음. G009 보고서에는 "결과 없음"만 표기되어 원인 불명.
2. **산출물 위치 파악 어려움**: 리서치실 산출물 3개는 `docs/research/` 경로에 있지만, 파일명이 한국어여서 탐색이 번거로움.
3. **태스크-산출물 연결 단절**: 어느 태스크(Task ID)가 어느 산출물을 생성했는지 역추적 불가.
4. **재배정 기준 불투명**: `max_iterations_reached` 후 목표를 재설정할 때 어떤 조건이 충족되면 재시작이 가능한지 기준 없음.

#### 사용 시나리오 (G009 산출물 검토)

```
[상황] PM으로부터 "G009 산출물 검토해줘" 요청 수신
[채널] 부서 텔레그램 채널
[질문] "G009에서 우리 부서 산출물이 뭐야?"
[기대] 부서별 태스크 목록 + 산출물 파일 경로 + 미수신 원인
[다음] 산출물 품질 검토 후 승인/수정 요청 PM에 전달
```

## 3. 사용 시나리오 — User Journey

### 시나리오: G009가 `max_iterations_reached`로 종료된 후 PM이 결과를 조회하는 흐름

**트리거**: Rocky가 텔레그램에서 "G009 결과 어떻게 됐어?" 메시지 전송

---

#### Step 1: 트리거 — 결과 조회 요청

| 항목 | 내용 |
|------|------|
| **사용자 행동** | 텔레그램 PM 채널에 "G009 결과 어떻게 됐어?" 입력 |
| **현재 시스템 반응** | 원시 로그 텍스트 또는 응답 없음 |
| **사용자 감정** | 불안 (결과가 어떻게 됐는지 모름) |
| **기대 시스템 반응** | 구조화된 상태 요약 카드 즉시 표시 |
| **성공 기준** | 3초 이내 응답 수신 |

---

#### Step 2: 현황 파악 — 상태 배지 확인

| 항목 | 내용 |
|------|------|
| **사용자 행동** | 응답 메시지에서 상태 배지 확인 |
| **표시 정보** | `[STOPPED] max_iterations_reached` 배지 + 이터레이션 11/10 표기 |
| **사용자 감정** | 상태 이해 (완료 아님, 초과 종료) |
| **이탈 리스크** | 상태 명칭이 기술적이어서 뜻을 즉시 해석 못 하면 혼란 |
| **성공 기준** | 배지만으로 "달성 여부"를 5초 내 판단 가능 |

---

#### Step 3: 달성률 확인

| 항목 | 내용 |
|------|------|
| **사용자 행동** | 달성률 수치 확인 |
| **표시 정보** | `0/2 KR 달성 (0%)` + confidence `0.0` |
| **사용자 감정** | 실망 + "산출물은 있는데 왜 0%지?" 의문 |
| **이탈 리스크** | 산출물 3개 생성과 달성률 0%의 모순이 설명 없이 표시되면 혼란 |
| **성공 기준** | 달성률과 산출물 수가 별도 항목으로 명확히 구분되어야 함 |

---

#### Step 4: 산출물 목록 확인

| 항목 | 내용 |
|------|------|
| **사용자 행동** | 산출물 파일 목록 스캔 |
| **표시 정보** | 부서별 산출물 목록 (파일명 + 경로) + 미수신 부서 목록 |
| **사용자 감정** | "리서치실은 했구나, 기획실은 왜 없지?" |
| **이탈 리스크** | 파일 경로만 표기되면 파일 내용을 확인하기 위해 터미널 전환 필요 |
| **성공 기준** | 어떤 부서가 무엇을 했는지 한눈에 파악 (10초 이내) |

---

#### Step 5: 미달성 원인 파악

| 항목 | 내용 |
|------|------|
| **사용자 행동** | 종료 사유 확인 |
| **표시 정보** | "이터레이션 한도 초과 (11/10)" + "기획실/디자인실 결과 미수신" |
| **사용자 감정** | 원인 이해 + 재시작 가능 여부 판단 필요 |
| **이탈 리스크** | 원인 목록 없이 "max_iterations_reached"만 표시되면 "왜?"를 알 수 없어 후속 결정 불가 |
| **성공 기준** | 미달성 원인 2가지(한도 초과 / 태스크 미수신)가 명확히 분리되어야 함 |

---

#### Step 6: 후속 액션 결정

| 항목 | 내용 |
|------|------|
| **사용자 행동** | 후속 액션 선택 |
| **옵션** | (A) 목표 재설정하여 G010 시작 / (B) 산출물 활용으로 마무리 / (C) 현 상태 보존 |
| **사용자 감정** | 결정 압박 (빠른 판단 필요) |
| **이탈 리스크** | 옵션이 없으면 사용자가 직접 DB를 수정해야 하는 상황 발생 |
| **성공 기준** | 텔레그램 내에서 후속 명령 입력으로 후속 액션 실행 가능 |

## 4. 핵심 정보 우선순위 (Information Architecture)

GoalTracker 결과 화면에서 사용자가 보고 싶은 정보를 우선순위 순으로 정의한다.

### 우선순위 계층

```
[GoalTracker 결과 메시지 — 텔레그램]
│
├── [P0: 즉각 인식] 상태 배지
│   ├── COMPLETED   (목표 달성)
│   ├── STOPPED     (max_iterations_reached — 이터레이션 초과)
│   ├── STAGNATED   (정체 판정 후 중단)
│   ├── IN_PROGRESS (진행 중)
│   └── CANCELLED   (수동 취소)
│
├── [P1: 핵심 지표] 달성률
│   ├── KR 달성 수 / 전체 KR 수  (예: 0/2)
│   ├── 달성률 %                  (예: 0%)
│   └── confidence 점수           (예: 0.0)
│
├── [P2: 종료 맥락] 종료 사유
│   ├── 종료 코드                 (max_iterations_reached)
│   ├── 이터레이션 현황           (11/10)
│   └── 미달성 원인 목록          (한도 초과 / 특정 부서 미수신)
│
├── [P3: 결과물] 산출물 목록
│   ├── 부서별 산출물 파일 목록
│   ├── 미수신 부서 목록
│   └── 각 산출물의 요약 1줄
│
└── [P4: 다음 단계] 후속 액션 추천
    ├── (A) 목표 재설정 명령어 제안
    ├── (B) 산출물 검토 명령어 제안
    └── (C) 현 상태 유지
```

### 텔레그램 메시지 포맷 설계안 (ASCII 와이어프레임)

```
┌─────────────────────────────────────┐
│ [STOPPED] G-aiorg_pm_bot-009        │  ← P0: 상태 배지
│ AIMesh 경량화·대시보드·오픈소스화  │
├─────────────────────────────────────┤
│ 달성률: 0/2 KR (0%)                 │  ← P1: 핵심 지표
│ 신뢰도: 0.0 | 이터레이션: 11/10    │
├─────────────────────────────────────┤
│ 종료 사유                           │  ← P2: 종료 맥락
│ • 이터레이션 한도 초과 (11 > 10)   │
│ • 기획실/디자인실 결과 미수신       │
├─────────────────────────────────────┤
│ 산출물 (리서치실 3개 완료)          │  ← P3: 결과물
│ 1. 경량화_대상_컴포넌트_분석표.md  │
│ 2. 실시간_대시보드_기술스택_비교표  │
│ 3. 만화캐릭터_대시보드_레퍼런스    │
│ 미수신: 기획실, 디자인실, 운영실   │
├─────────────────────────────────────┤
│ 후속 액션                           │  ← P4: 다음 단계
│ [A] 목표 재설정 → /goal new G009   │
│ [B] 산출물 검토 → /goal report 009 │
│ [C] 현 상태 유지 (조치 없음)        │
└─────────────────────────────────────┘
```

### 정보 우선순위 근거

| 우선순위 | 항목 | 근거 |
|---------|------|------|
| P0 — 상태 배지 | 즉각 인식 | 사용자가 텍스트를 읽기 전에 상태를 색상/이모지/레이블로 직관 파악. 5초 내 "달성됐나, 안 됐나" 판단 |
| P1 — 달성률 | 핵심 지표 | "얼마나 됐어?"가 두 번째 질문. KR 수치는 산출물 수와 별개로 명확히 표기되어야 모순 해소 가능 |
| P2 — 종료 사유 | 의사결정 맥락 | "왜 안 됐어?"가 세 번째 질문. 원인 없이는 후속 액션 결정 불가 |
| P3 — 산출물 목록 | 성과 가시화 | 달성률 0%라도 부분 성과(산출물)가 있으면 명시해야 재활용 가능. PM이 "그나마 건진 게 뭐야?" 질문에 답 |
| P4 — 후속 액션 | 마찰 제거 | 결과 확인 후 다음 단계로 넘어가는 전환 마찰을 최소화. 명령어 제안으로 복잡한 입력 불필요 |

## 5. WCAG 접근성 요구사항

텔레그램 환경에서 GoalTracker 결과 메시지에 적용할 접근성 요구사항.

### 5.1 텔레그램 환경 특성 및 제약

| 특성 | 접근성 영향 |
|------|------------|
| 텍스트 전용 채널 | 이미지/CSS 스타일 불가 — 구조는 기호/이모지로만 표현 |
| 모바일 우선 | 작은 화면에서 가독성 확보 필요 — 길이 제한 중요 |
| 다크/라이트 모드 자동 전환 | 배경 색상 가정 불가 — 색상 의존 표현 금지 |
| 스크린 리더 미지원 | 텔레그램 자체 접근성 API 의존 — 텍스트 구조가 의미를 담아야 함 |
| 알림 팝업 미리보기 | 첫 1~2줄이 가장 먼저 노출 — P0 정보를 최상단에 배치 필수 |

### 5.2 WCAG 2.1 AA 적용 가이드라인

#### (1) 색상 의존 금지 (Success Criterion 1.4.1)

**요구사항**: 색상만으로 상태를 구별하지 않는다.

- **금지**: 빨간색 텍스트로만 "실패" 표시 (텔레그램 텍스트 색상 제어 불가)
- **적용**: 이모지 + 텍스트 레이블 조합 필수

```
# 올바른 패턴
[STOPPED] ⛔ max_iterations_reached
[COMPLETED] ✅ 목표 달성
[IN_PROGRESS] ⏳ 진행 중

# 잘못된 패턴 (색상만 의존)
max_iterations_reached  ← 이모지/레이블 없이 텍스트만
```

#### (2) 텍스트 대비 및 가독성 (Success Criterion 1.4.3)

**요구사항**: 텔레그램 마크다운(`**bold**`, `` `code` ``)을 활용하여 계층 구조 표현.

- 상태 배지: `**[STOPPED]**` — 볼드로 시각적 강조
- 수치 데이터: `` `0/2 KR` `` — 코드 블록으로 구별
- 파일 경로: `` `docs/research/경량화_분석표.md` `` — 코드 블록 처리

#### (3) 일관된 내비게이션 (Success Criterion 3.2.3)

**요구사항**: 모든 GoalTracker 결과 메시지는 동일한 섹션 순서(P0→P1→P2→P3→P4)를 유지한다.

- 사용자가 여러 목표의 결과를 비교할 때 위치 기반 예측이 가능해야 함
- G009, G010, G011 결과 메시지 모두 동일한 구조

#### (4) 오류 식별 및 설명 (Success Criterion 3.3.1)

**요구사항**: `max_iterations_reached` 상태를 단순 코드가 아닌 설명과 함께 표시한다.

```
# 올바른 패턴
종료 사유: 이터레이션 한도 초과 (11회/10회 허용)
→ 목표가 자동 종료됩니다. 재설정하려면 /goal new [설명]을 입력하세요.

# 잘못된 패턴
status: max_iterations_reached
```

#### (5) 충분한 시간 (Success Criterion 2.2.1)

**요구사항**: GoalTracker 결과 메시지는 영구 보존되어야 하며, 자동 삭제/만료 없음.

- 텔레그램 채팅 히스토리 보존 정책에 의존
- 메시지에 타임스탬프 명시: `종료: 2026-04-01 05:35 KST`

#### (6) 언어 명확성 (Success Criterion 3.1.3)

**요구사항**: 기술 용어는 한국어 설명을 병기한다.

| 기술 용어 | 병기 설명 |
|-----------|-----------|
| `max_iterations_reached` | 이터레이션 한도 초과 |
| `confidence` | 신뢰도 (0.0 = 달성 불확실) |
| `KR` | 핵심 결과 지표 (Key Result) |
| `stagnated` | 진행 정체 (반복해도 진전 없음) |

### 5.3 모바일 가독성 요구사항

| 요구사항 | 기준 |
|---------|------|
| 메시지 총 길이 | 스크롤 없이 핵심 정보(P0~P2) 표시 가능 (약 15줄 이내) |
| 한 줄 최대 길이 | 40자 이내 (한글 기준, 모바일 화면 깨짐 방지) |
| 산출물 목록 | 최대 5개까지 인라인 표시, 초과 시 "외 N개" 축약 |
| 후속 액션 | 명령어는 `/` 접두어로 시작하여 텔레그램 자동완성 활용 |

## 6. 리서치 인사이트 요약

### 핵심 인사이트

| # | 인사이트 | 설계 방향 |
|---|---------|----------|
| 1 | PM은 "달성/미달성"을 먼저 묻고, "왜?"를 두 번째로 묻는다 | 상태 배지(P0)와 종료 사유(P2)를 분리하되 P2를 즉시 열람 가능하게 |
| 2 | 달성률 0%와 산출물 3개의 공존은 모순처럼 보인다 | 달성률(KR 기준)과 산출물 수(부서 기여)를 별개 항목으로 명확히 구분 |
| 3 | `max_iterations_reached`는 기술 용어다 — PM에게는 불투명 | 한국어 설명 병기 + 재설정 방법 안내로 즉각 행동 유도 |
| 4 | 부서별 참여 현황이 보이지 않으면 "누가 했고 누가 안 했나?"를 알 수 없다 | 산출물 목록에 부서 레이블 + 미수신 부서 목록 병기 |
| 5 | 결과 확인 후 후속 액션까지의 마찰이 높다 | 후속 명령어 추천(P4)으로 한 번의 입력으로 다음 단계 전환 가능 |
| 6 | 텔레그램은 색상/CSS를 지원하지 않는다 | 이모지 + 볼드 + 코드 블록으로 시각 계층 표현 (WCAG 1.4.1) |

### Phase 2 설계 과제 (와이어프레임 대상)

이 문서에서 도출된 인사이트를 바탕으로 Phase 2에서 설계할 항목:

1. **GoalTracker 결과 메시지 컴포넌트**: P0~P4 섹션별 텔레그램 마크다운 템플릿
2. **상태 배지 시스템**: 5개 상태(COMPLETED/STOPPED/STAGNATED/IN_PROGRESS/CANCELLED) 이모지+레이블 매핑
3. **후속 액션 플로우**: 결과 확인 → 후속 명령어 입력 → 목표 재설정 전체 흐름
4. **부서별 참여 현황 표**: 산출물 있음 / 미수신 / 태스크 미배정 3가지 상태 표현
