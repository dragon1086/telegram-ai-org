### 2.1 사용자 시나리오 3가지

#### 시나리오 A — "목표 달성 확인" (완료 컨텍스트)

```
사용자: PM Rocky
트리거: 아침 목표 리포트에서 ✅ 완료 배지 확인
행동 흐름:
  1. 상태 요약 카드에서 달성률 100% + KR 2/2 완료 확인
  2. 프로그레스 바 완전 채워진 시각 피드백 수신
  3. 주요 산출물 링크 확인 (2~3개 bullet)
  4. [📁 아카이브] 버튼 탭 → 완료 처리
성공 기준: 10초 이내 달성 여부 판단, 산출물 확인, 아카이브 1탭 완료
실패 위험: 완료 상태인데 경고 스타일 표시 → severity 분기 철저히 구분
```

#### 시나리오 B — "진행중 상태 점검" (진행중 컨텍스트)

```
사용자: 팀 리더
트리거: 중간 점검 명령어 입력 (/goal G009 status)
행동 흐름:
  1. 현재 달성률(예: 45%) + 이터레이션 잔여(예: 6/10 남음) 확인
  2. KR별 진행 상황 드릴다운 (어떤 KR이 블로킹 중인지)
  3. 다음 체크포인트 일정 확인
  4. 필요 시 [⚙️ 리플랜 요청] 버튼 탭
성공 기준: 30초 이내 현재 상태 파악 + 다음 조치 결정
실패 위험: 남은 이터레이션 수가 부각되지 않으면 마감 임박 인식 실패
```

#### 시나리오 C — "보류/중단 원인 파악" (강제종료 컨텍스트 — G009 실제 상황)

```
사용자: PM Rocky
트리거: 아침 리포트에서 🔴 강제종료 배지 발견
행동 흐름:
  1. 헤더에서 이터레이션 초과(11/10) 즉시 인지
  2. 달성률 0% + 서브태스크 19개 전원 취소 현황 확인
  3. [🔍 원인분석] 탭 → AI 분석 리포트 요청
  4. 분석 결과 수신 후 재등록/아카이브 결정
성공 기준: 강제종료 사유를 60초 이내 파악, 후속 액션 선택 완료
실패 위험: "강제종료"라는 단어로 인한 부정적 감정 → 중립적 표현("이터레이션 한도 도달") 사용
```

| Severity | 레이블 | 이모지 | 헥스 코드 | 색상명 | 대비율(on white) | WCAG 등급 | 적용 상황 |

**Severity 자동 결정 규칙**

```
목표 상태 → Severity 매핑:
  status == 'completed'            → INFO-OK  (Green)
  status == 'in_progress'
    AND iteration_remaining >= 4   → INFO     (Blue)
    AND iteration_remaining <= 3   → WARNING  (Orange)
  status == 'on_hold'              → WARNING  (Orange)
  status == 'max_iterations_reached'
  OR status == 'cancelled'         → CRITICAL (Red)

서브태스크 상태 매핑:
  completed  → INFO-OK  ✅
  in_progress → INFO    🔄
  pending    → NEUTRAL  ⏳
  cancelled  → NEUTRAL  ⚫
```

**색상 외 구분 수단 (색맹 대응, WCAG 1.4.1)**

- 모든 severity는 **이모지 아이콘 + 텍스트 레이블** 이중 표현 필수
- 예: `❌ 강제종료` (아이콘+텍스트), `⚠️ 경고` (아이콘+텍스트)
- 색상 단독으로 정보를 전달하는 패턴 금지

| # | WCAG 기준 | 항목명 | 구현 방법 | 충족 여부 |
|---|-----------|--------|----------|----------|
| 1 | 1.4.1 Use of Color | **색상 단독 정보 전달 금지** | 모든 상태에 이모지 아이콘 + 텍스트 레이블 병행. `❌ 강제종료`, `✅ 완료` 텍스트 필수. | ✅ |
| 2 | 1.1.1 Non-text Content | **이모지/아이콘 텍스트 대체재** | 이모지만으로 의미를 전달하지 않음. 모든 이모지 옆에 텍스트 설명 병기. 스크린리더 환경에서도 의미 전달 가능. | ✅ |
| 3 | 1.4.3 Contrast Minimum | **텍스트 대비율 AA 기준 충족** | CRITICAL Red #D32F2F: 5.7:1 ✅ / INFO-OK Green #388E3C: 5.1:1 ✅ / INFO Blue #0288D1: 4.6:1 ✅ / NEUTRAL Grey #757575: 4.6:1 ✅ (모두 4.5:1 기준 충족) | ✅ |
| 4 | 2.5.5 Target Size | **인라인 버튼 터치 타겟 최소 44×44px** | 텔레그램 인라인 키보드 버튼은 기본 최소 44×44px 보장. 버튼 텍스트에 충분한 여백 확보. | ✅ |
| 5 | 3.3.1 Error Identification | **에러 상태 명확한 텍스트 식별** | 에러 유형별 제목 + 원인 설명 + 해결 방법 3단 구조. "데이터 로드 실패", "목표 미발견" 등 구체적 레이블. | ✅ |
| 6 | 3.3.4 Error Prevention | **비가역적 액션 오류 방지** | 아카이브 버튼에 `⚠️` 레이블 + 확인 다이얼로그 2단계 필수. "되돌릴 수 없습니다" 경고 문구 명시. | ✅ |
| 7 | 2.4.6 Headings and Labels | **섹션 헤더 및 레이블 명확성** | 각 섹션 구분선(`━━━`) + 섹션명(KR 달성 현황, 서브태스크 현황, 산출물 현황) 명시. 레이블 없이 수치만 나열하지 않음. | ✅ |
| 8 | 1.3.1 Info and Relationships | **정보 구조 계층 텍스트 표현** | 헤더 > 본문 > 푸터 3단 구조를 구분선으로 시각화. ASCII 계층 구조 활용. 중요도별 들여쓰기 적용. | ✅ |
| 9 | 2.4.4 Link Purpose | **버튼/링크 목적 명확성** | 모든 버튼 텍스트에 동사+목적어 구조: `📁 아카이브`, `🔍 원인분석`, `📋 상세 보기`. "여기 클릭" 같은 불명확한 레이블 금지. | ✅ |
| 10 | 3.2.2 On Input | **사용자 입력 예측 가능한 동작** | 버튼 탭 시 예상 동작을 버튼 텍스트에 명시. 장시간 작업은 소요 시간 사전 안내(`약 2~3분`). 즉각 로딩 메시지 제공으로 무응답 방지. | ✅ |

## 설계 결정 근거 요약

1. **요약-상세 2단계 구조**: PM(의사결정자)은 30초 이내 핵심 3개 수치(달성률/이터레이션/종료시각) 파악 → 팀 리더는 필요 시 드릴다운 진입. 역할별 정보 소비 패턴 반영.
2. **3가지 상태별 분기 설계**: G009의 실제 상태(강제종료)뿐 아니라 완료/진행중 상태도 설계하여 범용 goal 추적 UI 패턴으로 확장 가능.
3. **Severity 3단계 자동 결정**: 코드 기반 severity 매핑 규칙으로 디자인 일관성 유지. 인간이 수동으로 배지를 선택하지 않음.
4. **에러 UX 3유형**: 단순 에러 메시지가 아닌 원인+대안 제시 패턴으로 사용자 불안감 최소화.
5. **접근성 10항목 전체 충족**: 텔레그램 텍스트 기반 환경에서도 WCAG 2.1 AA 기준 달성 가능함을 입증.
